## 1. Executive Summary

**整體評估：Cairn 的基礎品質很好，問題集中在甘特圖的視覺層，以及幾個一致性缺口。** 本次沒有發現 Critical 問題；所有主要流程都能完成，全程沒有 console error。

Design system、狀態回饋、破壞性操作的文案、拖曳預覽和 Auto 排程預覽，都達到成熟產品的水準。Cairn 與 Linear 級質感的差距不在元件，而在甘特圖的畫面噪音，以及「操作後能不能安心」這類細節。

**最值得優先處理的 5 件事**

| #   | 問題                                                                              | 嚴重度 | 複雜度 |
| --- | --------------------------------------------------------------------------------- | ------ | ------ |
| 1   | **背景窗格感（需求 B）**：週末色帶與階段列顏色幾乎相同，把工作日切成一格格方塊    | High   | S      |
| 2   | **任務長條半透明、外部標籤沒有遮罩**：今日線與依賴線穿過文字，所有刻度都有        | High   | S      |
| 3   | **階段沒有顏色（需求 A）**：所有長條同一色相，階段的邊界要靠左欄才看得出來        | High   | M      |
| 4   | **甘特圖拖曳無法復原，也沒有存檔後的回饋**：誤拖後要自己記得原本的日期            | High   | S–M    |
| 5   | **已完成任務也算衝突，「Resolve all」會搬動它們**：紅色訊號失真，也會改寫歷史日期 | High   | S–M    |

第 1、2 項合計約半天到一天，是本次投入報酬最高的改善。我已用 CSS 注入模擬驗證效果，見 §8。

Task Modal 的混合儲存模型（X-1）也是 High，但需要你先做產品決策，所以沒有排進前 5。

## 3. 產品 UI/UX 優勢

以下做得好，**後續改動應該保留**。

1. **Shell 退到背景。** 較暗的側邊欄搭配圓角內嵌主面板，內容明顯優先。
2. **Token 紀律很好。** 深淺主題共用一套結構，對比已系統化驗證。
3. **拖曳回饋成熟。** 拖曳中同時顯示原位虛線與 `Nov 10 – Nov 11 · 2 days +3 days` 提示。![拖曳提示](ux-audit-assets/gantt-drag-tooltip.png)
4. **建立依賴的回饋清楚。** 拖曳時即時高亮目標，並用文字顯示「誰 → 誰」。![建立依賴](ux-audit-assets/gantt-link-drawing.png)
5. **Auto 排程先預覽。** 舊日期→新日期、Δ 天數、時間軸上的虛線預覽，確認後才寫入。
6. **破壞性操作說明後果。** 例如「Its 1 task becomes ungrouped (No phase). Nothing else is deleted.」，專案刪除則列出影響的任務數。![刪除階段](ux-audit-assets/phase-delete.png)
7. **未排程任務有直接操作的入口。** 列上提示「Drag across a row to schedule it · double-click for a one-day task」。
8. **甘特圖結構紮實。** 左右列對齊量測零誤差，切換刻度會維持中心日期，捲動時標籤黏住可視邊緣，依賴線可點選並用 Delete 刪除，刪除後可 Undo。![選取依賴線](ux-audit-assets/gantt-dep-selected.png)
9. **List 行內輸入流暢。** 連續輸入 + Enter 可以一次建立多筆任務，焦點留在輸入框。
10. **日期語意友善。** Today、Yesterday、逾期圖示加文字，不只靠顏色。

### 5.2 需求 B：背景矩形色塊

**結論：問題不只在週末色帶，而是三層背景疊出了窗格。** 我用像素取樣確認了成因。

| 圖層     | 實測顏色                                        | 成因                                            |
| -------- | ----------------------------------------------- | ----------------------------------------------- |
| 工作日   | `rgb(255,255,255)`，寬約 79px                   | 白底                                            |
| 週末色帶 | `rgb(248,248,248)`，寬 32px，佔 Week 時間軸 29% | `--gantt-weekend`，由 `scale.ts:361` 依週平鋪   |
| 階段列   | `rgb(248,248,250)`，不透明                      | 右側車道也使用 `bg-muted`（`GanttRow.tsx:155`） |

週末色帶與階段列的對比只有 **1.001:1**，肉眼無法分辨，於是直向色帶與橫向色帶融成同一張格網，把白色工作日框成一塊塊方格。週末和白底的對比雖然只有 1.062:1，但大面積重複的硬邊仍然很明顯。

往右捲動到沒有任務的區域時最明顯，畫面只剩方塊：

![捲動後的窗格](ux-audit-assets/gantt-scrolled-right.png)

Month 刻度沒有週末色帶，看起來就乾淨得多，這也佐證了成因：

![Month 刻度](ux-audit-assets/gantt-month.png)

#### 建議規格

| 元素                | 現況                | 建議                                                               |
| ------------------- | ------------------- | ------------------------------------------------------------------ |
| **週末（Week）**    | 整欄色帶            | 移除                                                               |
| **週末（Day）**     | 整欄色帶            | 主體移除，**只保留表頭儲存格的底色**（已存在，`TimeAxis.tsx:107`） |
| **每日格線（Day）** | 每 36px 一條        | 移除；只在拖曳時顯示所在日期的導引                                 |
| **每週格線**        | Day 較深、Week 較淺 | 兩者都用同一條極淡髮絲線（`--border-subtle`）                      |
| **月份線**          | 1px 較深            | 保留；若與週線相鄰 1–2 天則略過週線，避免雙線                      |
| **階段列右側**      | 不透明 `bg-muted`   | 改為透明，讓時間軸連續；左欄維持底色以保留層級                     |
| **今日線**          | 1.5px 實色          | 1px、約 55% 不透明度，靠 Today pill 定位                           |

**為什麼可以拿掉週末色帶？** Auto 排程本來就以連續日曆日計算，排程對話框也寫明「weekends included」，所以週末不影響 Cairn 的排程邏輯。Day 刻度的表頭仍會標示週末。這一點仍是【假設】，要實際使用幾天確認。

**實作考量（S）**

- 修改 `scale.ts` 的 `gridBackgroundStyle`，同步更新 `scale.test.ts:228`。
- Timeline 共用同一個函式（`TimelineChart.tsx:182`），會自動得到相同改善。
- 繼續使用 CSS gradient，不新增 DOM 節點，效能不受影響。

### 5.3 需求 A：階段顏色

**現況**【程式】：`Phase` 型別與 `phases` 資料表都沒有顏色欄位，長條顏色只由狀態決定。

#### 建議設計

| 元素                 | 樣式                             | 理由                     |
| -------------------- | -------------------------------- | ------------------------ |
| **階段列（左欄）**   | 名稱前加 8px 色點                | 低調的身分標記           |
| **彙總括號**         | 實色                             | 階段範圍一眼可見         |
| **To Do 長條**       | 填色 16% + 階段色邊框            | 與現有視覺重量相近       |
| **In Progress 長條** | 填色 30% + 階段色邊框 + 左側粗邊 | 保留現有的狀態形狀       |
| **Done 長條**        | 填色 8% + 邊框 40%               | 退到背景但保留歸屬       |
| **衝突**             | 紅色邊框覆蓋階段色               | 訊號優先於身分           |
| **逾期**             | 紅色端點維持不變                 | 同上                     |
| **任務與子任務**     | 一律繼承，不提供個別設定         | 維持輕量                 |
| **文字**             | 維持中性文字色                   | 確保可讀                 |
| **里程碑**           | 維持深色菱形                     | 高對比，且與長條形狀不同 |
| **List、Board**      | 階段標題與晶片加色點             | 一份資料到處一致         |

狀態仍由圖示與填色深淺表達，所以「顏色不是唯一訊號」的原則不變。

**對比驗證**（9 色、深淺主題，以 sRGB 混色估算，與實際 oklab 混色略有差異）

| 組合             | 淺色最低值 | 深色最低值 | 目標  |
| ---------------- | ---------- | ---------- | ----- |
| 文字 on 16% 填色 | 12.06      | 10.71      | ≥ 4.5 |
| 文字 on 30% 填色 | 9.81       | 7.48       | ≥ 4.5 |
| 邊框 vs 背景     | 3.56       | 6.16       | ≥ 3   |
| 邊框 vs 16% 填色 | 3.02       | 4.87       | ≥ 3   |

#### 互動

- 點階段標題的色點開啟色盤；階段選單新增 **Color**；New phase 對話框也提供。
- 色盤沿用專案的顏色元件與 `--project-*` tokens，新增一個 **Use project color** 選項。
- 建議**移除紅色**，避免與衝突、逾期的語意混淆（需要你決定，見 §10.1）。
- 未設定顏色時（`null`）繼承專案色，既有資料不受影響，也符合「顏色是訊號，不是裝飾」的原則。

#### 技術實作（M）

1. **資料**：`phases.color` 可為 null，加 migration 與 CHECK；更新 `Phase` 型別、`mappers.ts`、repository、`backup.ts`。Migration 由你決定何時套用到正式環境。
2. **向下相容（重要）**：`localRepository.ts:239-246` 的 `isTableOf` 會逐欄檢查，舊資料沒有 `color` 時值是 `undefined`。如果沿用只接受 `null` 的檢查，**整個本機工作區會被判定為無法讀取並移到備份鍵**。我的測試資料寫錯時就實際觸發過這條路徑。檢查必須接受缺值，舊備份的匯入也要加測試。
3. **渲染**：在列上設定 `--phase-color`，重新定義 `--gantt-bar-fill` 等 token，例如 `color-mix(in oklab, var(--phase-color, var(--accent)) 16%, var(--gantt-bg))`。元件幾乎不用改，而且填色會變成不透明，同時解決 G-3。
4. **共用**：把 `timeline/ProjectRow.tsx:43` 的 `PROJECT_COLOR_VAR` 移到共用位置。

## 6. 問題清單與嚴重度

**統計：Critical 0、High 6、Medium 14、Low 12。**

### 6.1 High

#### G-1 背景窗格感（需求 B）

- **頁面**：Gantt、Timeline
- **類型**：【觀察】【程式】
- **描述與證據**：見 §5.2。工作日被週末與階段列切成方塊，兩者對比僅 1.001:1。
- **影響**：背景的對比節奏比任務還搶眼，直接削弱精緻感與掃讀效率。
- **建議**：§5.2 的規格。
- **複雜度**：S

#### G-2 階段沒有顏色（需求 A）

- **頁面**：Gantt（延伸到 List、Board）
- **類型**：需求；成因【程式】
- **描述與證據**：所有未完成長條都是同一藍紫色，看右側時必須回頭對照左欄才知道屬於哪個階段。
- **影響**：多階段專案難以看出工作的分布與重疊。
- **建議**：§5.3。
- **複雜度**：M

#### G-3 今日線與依賴線穿過文字

- **頁面**：Gantt、Timeline
- **類型**：【觀察】【程式】
- **描述與證據**：長條 `z-[2]` 雖在今日線之上，但填色半透明（`--gantt-bar-fill` 只有 14–24%），線條仍透出來穿過條內文字。條外標籤則完全沒有背景，例如「競品分析 Comp|etitive analysis」「品牌識|別審查」。深色模式相同。
- **影響**：每個含今天的畫面都會發生，降低閱讀品質，也是畫面顯得雜亂的第二大原因。
- **建議**：長條改為不透明填色（`color-mix` 混背景色）；條外標籤加與背景同色的底。模擬中文字陰影只能部分改善（見 §8），實作時應改用實色底。
- **複雜度**：S

#### G-4 甘特圖拖曳無法復原，也沒有存檔回饋

- **頁面**：Gantt
- **類型**：【觀察】
- **描述與證據**：移動任務後 `Nov 7–8` 變成 `Nov 10–11`，沒有任何提示，按 `⌘Z` 日期不變。同一個圖上刪除依賴卻有 Undo（`GanttChart.tsx:819`），My Tasks 改狀態也有。
- **影響**：長條大面積可拖、點擊與拖曳僅差 3px，誤拖後要自己記得原日期。
- **建議**：放開後顯示低調 toast `Moved to Nov 10 – Nov 11 · Undo`，沿用 `useTaskStatusChange.ts` 的模式；批次排程同樣提供。之後再考慮單層 `⌘Z`。
- **複雜度**：S–M

#### G-5 已完成任務也算衝突，Resolve all 會搬動它們

- **頁面**：Gantt
- **類型**：【觀察】【程式】；規則是否要改屬【偏好】
- **描述與證據**：`findConflicts`（`scheduling.ts:96`）不看狀態。兩端都完成的任務仍顯示紅框與警示。「Resolve all」預覽中，綠勾的「競品分析」+3d、「需求文件」+5d 都被列入搬動。

  ![Resolve 對話框包含已完成任務](ux-audit-assets/gantt-resolve-done-tasks.png)

- **影響**：紅色訊號被已成定局的事情稀釋，使用者可能因此忽略真正的衝突；按下 Apply 會改寫已完成工作的日期。預覽有列出，所以不是無聲發生，但仍容易忽略。
- **建議**：任一端已完成時不算衝突，`computeAutoSchedule` 也不移動已完成任務。需要更新 D10 與對應測試。
- **複雜度**：S–M

#### X-1 Task Modal 的兩種儲存模型並存

- **頁面**：Task Modal
- **類型**：【觀察】；方向屬【偏好】
- **描述與證據**：
  - 標題、描述、狀態、優先度、日期、階段要按 Save。
  - 子任務與依賴立即寫入，畫面上用一行小字「Subtasks and dependencies save right away.」說明。
  - 設定兩個日期後按 Esc 會跳「Discard changes?」。
  - 新增子任務後 Save 仍是停用狀態；按 Cancel 不會提示，子任務也不會撤銷（實測）。
  - 從開啟任務到存好兩個日期要 6 次點擊。而 List 行內改日期是立即生效的，同一個欄位在不同位置規則不同。
- **影響**：使用者必須記住哪些欄位要存。每次編輯都多一步，也與「Linear 般的操作效率」的定位不符。
- **建議**（待決策）：屬性變更立即儲存，標題與描述在失焦時儲存，移除 Save 與 Cancel，並用既有的 Undo toast 兜底。這需要重新檢視目前的未存檔防護與衝突處理邏輯。
- **複雜度**：L

### 10.2 待驗證的假設

- 拿掉 Week 與 Day 主體的週末標示，不會妨礙使用者排程。
- 階段色不會與狀態圖示、語意色互相干擾，特別是階段數超過 5 個時。

- 使用者確實偏好立即儲存，而不是明確的 Save。
- 長條上的 Undo toast 不會在連續微調時造成干擾；若會，可合併連續操作。
