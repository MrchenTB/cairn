# 決策紀錄（Decision Log）

每筆決策：背景 → 決定 → 理由／取捨。技術細節以 `docs/architecture.md` 為準。

## D1 — 產品名稱：Cairn

- **決定**：產品命名為 **Cairn**（石堆路標：沿路標記里程碑、指出方向），標語沿用 PRD 的 _Plan clearly. Work simply._；Logo 為自繪的幾何石堆圖形。
- **理由**：PRD 要求使用自己的名稱與圖示、不得使用 Linear 商標。名稱集中在少數常數與 `Logo` 元件，日後可輕易更換。

## D2 — 前端技術棧沿用 PRD 推薦，但採用 2026-11 的現行版本

- **決定**：Vite 8、React 19、TypeScript 7（原生編譯器）、Tailwind CSS 4、Radix（`radix-ui`）＋自有 shadcn 風格元件、lucide-react、dnd-kit、zustand＋immer、react-router 8、Supabase。
- **理由**：完全符合 PRD 的推薦起點，沒有引入額外後端。官方樣板（create-vite 9）預設即為 TS 7＋oxlint，因此 lint 改用 oxlint（ESLint 尚未支援 TS 7 的 API）。
- **取捨**：多個套件是很新的大版本（react-router 8、react-day-picker 10、zod 4…），開發時一律以 `node_modules` 內的型別定義為準，而不是憑記憶。

## D3 — 本機 Node 23 與測試工具版本

- **背景**：本機 Node 為 v23.9（已 EOL 的奇數版），Vitest 5／jsdom 30 的 `engines` 排除了 Node 23。
- **決定**：使用 Vitest 5（與 Vite 8 對齊）＋ jsdom 27；npm 僅出現 EBADENGINE 警告，實際執行正常。`package.json` 宣告 `node >=22.22`。
- **建議**：使用者日後可升級到 Node 24 LTS；Cloudflare 建置環境使用其預設 LTS 版本即可。

## D4 — 資料存取：雲端（Supabase）＋「本機模式」

- **決定**：以 Repository 介面隔離資料存取。設定 `VITE_SUPABASE_URL` 與 publishable／anon key 時為**雲端模式**（登入＋RLS）；未設定時進入**本機模式**（資料存在此瀏覽器的 localStorage，免登入），介面永遠明確顯示「Local only — not synced」。
- **理由**：使用者尚未提供 Supabase 金鑰。PRD 要求「先把不依賴金鑰的內容做到可執行」；本機模式讓 App 可以立即試用，也讓 E2E 測試不需要雲端帳號。本機實作複製了資料庫的所有規則（階層、依賴、級聯刪除、原子性），避免兩種模式行為不一致。
- **注意**：本機模式**不是**雲端同步，也不會被包裝成雲端同步（PRD §9.2）。正式使用請完成 Supabase 設定。

## D5 — 樂觀更新＋精準回滾

- **決定**：所有寫入先更新畫面（List／Board／Gantt 立即一致），再寫入雲端；失敗時用 Immer inverse patches 只回滾那一筆變更，並跳出含「Retry」的錯誤提示，側邊欄同步狀態顯示「Couldn't save」。
- **理由**：拖曳類操作需要即時回饋，同時滿足「不得虛報儲存成功」與「失敗可重試或回復」。

## D6 — 里程碑為獨立資料表

- **決定**：`milestones` 與 `tasks` 分開（PRD §5 建議）。依賴關係只存在於任務之間。
- **理由**：里程碑永遠不會被算進進度分母，也不會出現在看板欄位中；模型簡單、不易出錯。
- **取捨**：V1 不支援「任務 → 里程碑」的依賴線。

## D7 — 子任務限制一層

- **決定**：Project →（可選 Phase）→ Task →（可選）Subtask，只允許一層子任務；資料庫 trigger 與前端驗證都會擋。子任務自動跟隨父任務的 Phase。
- **理由**：PRD §5.1 允許此限制，可大幅降低排序、甘特圖與進度計算的複雜度。介面會在相關位置說明。

## D8 — 手動排序：fractional index

- **決定**：`sort_order` 使用 fractional-indexing 字串鍵（資料庫欄位 `COLLATE "C"`）。專案內所有頂層任務共用一個排序空間（跨 Phase、跨狀態），子任務在同一父任務下排序。
- **理由**：每次拖曳只需更新一列；List 群組與 Board 欄位都是同一排序的子序列，所以「插入兩個相鄰項目之間」永遠合法。看板內同欄排序只改 `sort_order`，不會動到狀態或日期（PRD §4.6）。

## D9 — 日期語意與時區

- **決定**：所有專案／任務／里程碑日期以 `YYYY-MM-DD` 日曆日期儲存（Postgres `date`），計算完全使用日曆算術，不經過 `Date` 的時區轉換。「今天」依使用者設定的時區（預設為首次使用時的瀏覽器時區，例如 Asia/Taipei）計算，並同步到雲端，所以不同電腦看到的 Today／Overdue 一致。
- **理由**：PRD §5.3 明確要求避免跨時區跳一天。

## D10 — 依賴與自動排程語意（V1）

- **決定**：只支援 Finish-to-Start、同專案、不得循環、不得父子互相依賴。日期為包含式、連續日曆日（不排除週末）。衝突判斷只標示「確定違反」的情況（只有截止日或只有開始日的任務用上下界判斷）。Manual（預設）只提示；Auto 先預覽受影響任務的舊→新日期，使用者確認後以單一 RPC 原子寫入。自動排程只會把後續任務往後推、保留工期，不會把任務往前拉。
- **理由**：符合 PRD §4.7 建議，避免不完整的工作日邏輯。

## D11 — 刪除父任務

- **決定**：刪除有子任務的父任務時，確認對話框讓使用者選擇「一起刪除子任務」或「保留子任務（提升為頂層任務，放在原父任務的位置）」，兩者都是原子操作。
- **理由**：PRD §5.1 要求明確確認子層的處理方式。

## D12 — 匯入策略

- **決定**：匯入備份一律「新增為複本」（重新產生所有 id），永遠不覆寫或刪除現有資料；整份檔案驗證通過才會以單一交易寫入。
- **理由**：最安全、不會意外破壞資料；要「還原」到空帳號時效果等同完整還原。

## D13 — 重試成功的回饋：統一顯示「Saved」，不重發各動作的確認

- **背景**：按下失敗提示的 Retry 後，失敗提示會消失、畫面也會更新，但沒有任何訊息說已存好；原動作的確認提示（例如「Project marked completed」＋Undo）不會再出現。
- **決定**：Store 在 Retry 真的重送並全部成功後，顯示一則通用的「Saved」提示。不新增各動作自己的確認回呼，重試後的變更也不提供 Undo。
- **理由**：PRD §5.4 要求明確的成功回饋，只需在 `retryInOrder` 加幾行就能做到。逐動作回呼要改動所有寫入路徑，對這種少見的情況不划算。
- **取捨**：重試成功後要撤銷，必須手動改回去。

## D14 — 雲端寫入尚未完成時離開頁面要提示

- **背景**：雲端模式下，寫入還在進行就關閉或重新整理分頁時，這筆寫入可能遺失，而且使用者沒有任何機會知道。
- **決定**：雲端模式且 `sync.pending > 0` 時，由 App Shell 掛上瀏覽器的 `beforeunload` 提示。本機模式的寫入是同步完成的，不掛。
- **理由**：這是 PRD §5.4「不得 silent failure」在關閉分頁時的缺口；可沿用 Task Modal 既有的 `useUnloadPrompt`，改動很小。
- **取捨**：請求卡住時，離開頁面會一直被提示；這個提示是真實的，因為那筆寫入確實還沒確認。此提示不等於離線佇列，已遺失的寫入不會自動補送。

## D15 — 自動排程預覽開啟時，切回分頁就立即重新讀取

- **背景**：焦點刷新有約 30 秒的節流。使用者在另一分頁改了日期，節流期間內切回來按 Apply，會用過期的計畫蓋掉剛才的修改。
- **決定**：`RescheduleDialog` 開啟且尚未送出時，視窗取得焦點或分頁重新可見就立即 silent refresh，跳過節流。預覽本來就依 store 即時重算，資料更新後清單會跟著變。不在 `apply_task_schedule` 做版本檢查。
- **理由**：這幾行就能處理實際會發生的情況。版本檢查要改 RPC 與資料合約，還要多一個衝突畫面，對單人使用的 V1 太重。
- **取捨**：其餘情況仍是後寫者勝，例如另一台裝置在預覽開啟期間修改、且這個分頁沒有失去過焦點，或刷新還沒回來就按下 Apply。

## D16 — 依賴約束不穿透沒有日期的任務

- **決定**：維持現行規則：只檢查直接相連、且確定違反的依賴。沒有自身日期的任務（包括只有子任務彙總範圍的父任務）不會把約束傳下去；連到它們的依賴線不畫、也不強制。Task Modal 的 Dependencies 區塊會在這種任務上用一行字說明。
- **理由**：這符合 D10「只標示確定違反」的原則，也符合 PRD §4.7「不能任意推測工期」。改成遞移式會改變衝突定義與預覽；把彙總範圍當成日期，則 Auto 必須移動子任務。
- **取捨**：A → 無日期 → C 可能排出先後錯亂的結果而不會警告，直到中間那個任務有日期為止。

## D17 — 甘特圖不支援在圖上把依賴拖到沒有日期的任務

- **決定**：圖上會說明「Schedule this task first to link it on the chart.」，這類連結由 Task Modal 建立。
- **理由**：連結存下後圖上既畫不出來，也不會有衝突提示，使用者得不到回饋。PRD §4.7 也沒有要求。

## D18 — 日期範圍維持完整的 0001–9999，不在輸入端加上限

- **背景**：同一專案的日期相距超過約 2,550 年（Day）或 5,700 年（Week，由計算推得）時，圖表會碰到 Chromium 的版面上限，超出的長條會被夾在邊界位置。
- **決定**：不加上限，列為已知限制。
- **理由**：日期只能從日曆選取，沒有打字輸入，也沒有年份下拉選單，打錯年份不會發生；實際上只有手改備份檔才到得了。崩潰已經修掉。加上限要同時改驗證、匯入規則與資料庫 check，也得處理既有資料，相對這個機率太重。

## D19 — 排序鍵允許相同

- **決定**：不加唯一索引，也不預留回滾可能用到的鍵。下列情況可能產生相同的 `sort_order`：回滾競態、遺失的回應、兩個分頁同時選到同一個鍵。相同時順序仍然穩定，匯入時會重新編鍵。
- **理由**：沒有資料風險，後果只是拖放落在兩個相同鍵之間時位置差一格。唯一索引要加 migration 與重新編鍵，還要處理跨裝置衝突；預留鍵只解決其中一種情況。

## D20 — 父任務狀態與子任務各自獨立

- **決定**：把有未完成子任務的父任務設為 Done 時，不詢問也不連動；子任務全部完成時，父任務也不會自動完成。進度只算 leaf task（PRD §5.2），未完成的子任務仍會出現在 My Tasks。
- **理由**：PRD 沒有規定連動，§11 要求次要互動採最簡單的預設，不要自行加功能。詢問對話框得放進 Task Modal、List、Board 拖曳與 My Tasks 所有改狀態的入口；完全由子任務推導則要改資料模型。
- **取捨**：可能出現 Done 的父任務底下還有未完成的子任務，或子任務都完成了父任務仍顯示 Overdue。這不影響進度數字。

## D21 — List／Board 不做虛擬捲動

- **決定**：不加 windowing，也不加「顯示更多」。實測（正式版、單一專案 900 個頂層任務）：List 首次繪製約 930 ms、Board 約 570 ms，互動都低於 300 ms。
- **理由**：這遠超過單人專案的實際規模。虛擬捲動會動到 dnd-kit 排序量測、鍵盤導覽與捲動定位，風險遠大於收益。
- **取捨**：單一專案任務數遠超這個規模時會明顯變慢；屆時先做「顯示更多」，仍不夠才做虛擬捲動。

## D22 — 事件時間戳沿用裝置時區

- **決定**：Settings 的備份／同步時間與 SyncIndicator 使用裝置時區，文案已標明；Task Modal 的建立／更新時間使用 `preferences.timezone`。兩者不統一。
- **理由**：這些時間要對得上眼前的裝置時鐘。PRD §5.3 談的是任務日期，任務日期不受影響。

## D23 — supabase-js 不改成動態載入

- **決定**：維持靜態 import，雖然本機模式也會載入這個約 165 KB（gzip）的 chunk。
- **理由**：正式使用都是雲端模式，一定用得到，動態載入省不到實際使用時的流量，反而要改 `src/data` 的模組載入方式。

## D24 — 已完成任務的日期是歷史：不自動改寫；successor 已完成的衝突為「歷史不一致」

- **決定**：（1）Auto 排程與「Resolve all」**不移動**狀態為 Done 的任務；使用者自己明確編輯的任務不受影響。被略過的 Done 任務會在預覽裡列出（「Completed — kept as they are」）。（2）successor 已完成的依賴違反，稱為「歷史不一致」，不計入衝突提示（紅框、衝突數、Resolve all），改在 Task Modal 以低調文字保留資訊。其餘（successor 未完成，包含 predecessor 已完成）仍是一般衝突，行為不變。
- **理由**：Done 任務的日期是已發生的事實，改寫會竄改歷史；而這類違反無法靠移動 successor 解決，列為紅色警示只會稀釋真正需要處理的訊號。
- **取捨**：D10 的「只標示確定違反」不變，只是把「已經無法補救」的那一類分開。更完整的分類（例如為歷史不一致提供「接受」操作、在甘特圖上以灰色虛線標示）列為後續建議，本次不做。
- **相依**：Done 任務的 successor 以它實際的完成日期為準，因此「被略過」不會讓後面的任務被推到不合理的位置。

## D25 — 階段顏色：以專案色票名稱儲存，null 表示沿用專案色

- **決定**：`phases.color` 為 `null | 色票名稱`（gray、blue、violet、pink、orange、yellow、green、teal；不含 red），不存 HEX。任務與子任務不另設顏色，一律繼承階段（無階段或未設定時用專案色）。Timeline 維持專案色，不使用階段色。
- **理由**：色票名稱對應 `--project-*` token，深淺主題自動正確；不含紅色是為了讓紅色只代表衝突、逾期與錯誤。`null` 讓既有資料零變動。
- **相容性**：本機儲存與備份缺少 `color`、或遇到未知色名時，一律讀成 `null`，不會把整份資料判為無法讀取。雲端寫入只在有顏色時才送出 `color` 欄位，所以尚未套用 migration 的資料庫仍能正常新增階段，只有「選顏色」需要先套用 migration。
