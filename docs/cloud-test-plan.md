# 真實雲端測試計畫（Staging）

目的：在**獨立的 Supabase 測試專案**上，驗證本機模擬器無法證明的事。全部通過前，不要把真實專案資料放上雲端。

規則：

- Staging 與 Production 是兩個獨立的 Supabase 專案，金鑰、帳號、資料都不共用。
- 測試帳號只放測試資料。
- 不用 `service_role`／`sb_secret_…` key。所有測試都以一般使用者身分執行，這樣測到的才是真實權限。
- Migration 一律先上 Staging，通過後才上 Production。

---

## 階段 0：建立 Staging 環境（需要你操作）

### 0.1 建立專案

1. 到 <https://supabase.com/dashboard> 建立專案，名稱 `cairn-staging`，Region 選 Northeast Asia (Tokyo)，Free 方案。
2. 資料庫密碼存進密碼管理工具。
3. 記下 **Project ref**（網址 `…/project/<project-ref>` 那一段）。

> Free 方案最多 2 個進行中的專案。Staging 加 Production 剛好用完。閒置約 7 天會被暫停，到 Dashboard 按 Resume 即可。

### 0.2 套用 Migration（擇一）

**方法 A：CLI（建議）**，在 repo 根目錄：

```bash
npx supabase@3.0.0 login
npx supabase@3.0.0 link --project-ref <staging 的 ref>
npx supabase@3.0.0 db push --remote --dry-run
npx supabase@3.0.0 db push --remote
```

`--dry-run` 應該列出**兩個**檔案。確認 link 到的是 Staging 再往下。

**方法 B：SQL Editor**，依序整份貼上執行，順序不能反：

1. `supabase/migrations/20261102000000_init.sql`
2. `supabase/migrations/20261106000000_phase_color.sql`

### 0.3 驗證 Schema

在 SQL Editor 貼上 `supabase/verify.sql` 整份執行。它只讀系統目錄，不會改任何東西。

**通過條件**：每一列 `pass = true`。失敗會排在最上面。

> 如果有失敗項目提到不是 Cairn 的函式或資料表（例如 Supabase 預設建立的物件），先不要處理，把那一列結果告訴我。（這份腳本已在全新的 cairn-staging 上跑過，18 列全部通過。）

再到 Dashboard 的 **Security Advisor** 看有沒有 RLS 相關錯誤。

### 0.4 設定 Auth

Dashboard → Authentication：

| 設定                       | 值                                                           |
| -------------------------- | ------------------------------------------------------------ |
| Site URL                   | `http://localhost:5183`（之後部署 Staging 網站時改成該網址） |
| Redirect URLs              | `http://localhost:5183`                                      |
| Allow new users to sign up | 建好測試帳號後**關閉**                                       |
| Confirm email              | 保持開啟（預設）                                             |

### 0.5 建立兩個測試帳號

Authentication → Users → **Add user → Create new user**，勾選 Auto Confirm。用你收得到信的信箱（重設密碼測試要收信），可以用加號地址，例如 `你的信箱+cairn-a@…`、`你的信箱+cairn-b@…`。

### 0.6 填寫本機設定

```bash
cp .env.staging.example .env.staging.local
```

填入 Project URL、publishable key、Project ref、兩組測試帳號。這個檔案已被 Git 忽略。**不要放 service role key。**

## 階段 1：自動化驗收（在你的電腦執行）

```bash
export PATH="$HOME/.local/node/current/bin:$PATH"
npm run test:staging
```

這組測試連到真實 Staging，涵蓋下表標「自動」的項目。它有四道防呆，任一不符就**拒絕執行**：

1. `.env.staging.local` 的 Project ref 必須和 URL 相符，所以不會誤連到別的專案。
2. 若設了 `CAIRN_PRODUCTION_PROJECT_REF`，URL 不得是那個專案。
3. 任何變數含 service role／secret key 就中止。
4. 測試帳號裡如果有不是測試建立的專案就中止，所以不會動到真實資料。

測試建立的專案名稱都以 `[e2e]` 開頭，結束時自行刪除。

本機想先試跑測試本身（連本機模擬器，不碰任何雲端）：`npm run test:staging:dry-run`。

結束後會清除測試專案與儲存的 session，耗時與效能數字留在 `test-results/staging/metrics.json`（已被 Git 忽略）。B5、P2、P3 的數字請貼給我，這些是之後判斷效能的基準。

測試進行中請不要闔上筆電，否則計時會失準，出現假失敗。

## 階段 3：部署 Staging 網站（需要你登入 Cloudflare）

跨裝置測試（D5、D6、D7）與 W 組需要網址。

```bash
npm run build:staging
npx wrangler@4.156.1 login
npx wrangler@4.156.1 deploy --env staging
```

部署後把網址（`https://cairn-staging.<帳號>.workers.dev`）加進 Staging 的 Site URL 與 Redirect URLs。Staging 維持關閉註冊。

## 階段 4：進入 Production 的條件

全部滿足才建立 Production：

- [ ] 自動化驗收全部通過
- [ ] R、A、S5、S7、D5、O3、B4、B6 手動項目全部通過或已接受風險
- [ ] 程式碼已推到私有遠端（目前只存在這台電腦）
- [ ] 備份流程已決定（見 `docs/production-readiness.md`）

Production 步驟與 Staging 相同，差別是：Site URL 與 Redirect URLs 用正式網址、建好自己的帳號後立刻關閉註冊、不放任何測試帳號。把 Production 的 ref 填進 `.env.staging.local` 的 `CAIRN_PRODUCTION_PROJECT_REF`，測試就不可能連到它。

**資料搬遷**：本機模式的資料在瀏覽器 localStorage，設定雲端金鑰後不會自動上傳，也不會被刪除。要搬上去，先在本機模式 Settings → Data 匯出 JSON，再於雲端模式匯入。
